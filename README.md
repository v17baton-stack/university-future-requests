# Университет будущего — обращения к конференции

Информационный сайт конференции 19 марта 2027 и Telegram-бот для обращений. Оформление: «Мягкое будущее». HTML, CSS и JavaScript без сборки; PostgreSQL и Edge Functions Supabase; Telegram webhook. Без React, Docker, VPS, платных API и опроса getUpdates.

## Фактическое состояние подключения

- GitHub-владелец: **v17baton-stack**.
- Выбран отдельный публичный репозиторий: `v17baton-stack/university-future-requests`.
- Supabase: подключение к аккаунту доступно; отдельный проект пока не создан, ожидается выбор организации пользователем.
- Telegram: новый бот, токен и проверенный ID владельца пока не предоставлены.
- `public/config.js` намеренно пустой; кнопка отправки отключена до подключения собственного облачного обработчика.
- Проверки на PGlite и тестовом Telegram-транспорте выполнены отдельно от живой системы. Они не означают, что сайт и бот уже запущены.

Ожидаемый адрес Pages после настройки: `https://v17baton-stack.github.io/university-future-requests/`. Наличие адреса в README не является подтверждением публикации.

## Что разрешено публиковать в GitHub

Все файлы исходников из этого комплекта, SQL-миграции, тесты, изображения, README, package.json, package-lock.json и workflows. GitHub Pages публикует **только `public/`**.

Нельзя публиковать `.local/`, env-файлы, токен Telegram, серверные ключи Supabase, секреты, реальные заявки и переписку. Они исключены в `.gitignore`; код проверок дополнительно сканирует публичные файлы. Данные приложения хранятся только в закрытой схеме `requests_app` в собственном Supabase.

## Настройка собственного подключения

1. Использовать только Supabase **Free** в согласованной организации. Не добавлять карту, платный план, платные ветки или дополнительные услуги.
2. Создать нового бота в настоящем [@BotFather](https://t.me/BotFather). Токен записать прямо в `.local/secrets.env`, не в чат и не в GitHub.
3. Применить обе миграции по порядку к новому отдельному проекту. Первая создаёт схему и таблицы, вторая — внутренние процедуры и шесть RPC. Чужие схемы не изменяются.
4. Разместить три Edge Functions и серверные секреты. Стандартный JWT-check отключается **только** у `create-application`, `telegram-hook`, `setup-telegram`: в них свои проверки. Для остальных функций ничего не меняется.
5. Зарегистрировать webhook через защищённую временную функцию. Запросы к Telegram выполняет облако Supabase. Накопленные updates не сбрасываются.
6. Для назначения владельца после подключения отправить `/id` в личном чате с собственным ботом. Этот ответ сообщает только ваш ID. Пользователь подтверждает, что это его аккаунт; ID сохраняется в `ADMIN_CHAT_ID` и переносится в облачные секреты. До этого форма не принимает обращения. Первый посетитель владельцем не становится.
7. Выполнить `status` и явно обозначенный `test` через временную функцию, затем живую приёмку с владельцем.
8. Вписать **собственный** URL `.../functions/v1/create-application` и username без @ в `public/config.js`. Это публичные значения; остальные секреты туда не попадают.
9. В GitHub: Settings → Pages → Source → GitHub Actions. Workflow `pages.yml` публикует только `public/`.
10. После успешной приёмки удалить **развёрнутую** `setup-telegram`, проверив её недоступность и сохранность двух рабочих функций. Исходник остаётся в Git.

### Секреты

`.local/secrets.env` создан локально. Независимые `TG_WEBHOOK_SECRET`, `SETUP_SECRET`, `FORM_SECRET` генерируются криптографически, по 48 URL-safe символов. Повторная подготовка не перезаписывает внесённые значения.

Обязательные поля: `BOT_TOKEN`, `BOT_USERNAME` (без @), `ADMIN_CHAT_ID`, `SITE_URL` (полный адрес с именем репозитория), три секрета. Для локального вызова временной облачной настройки добавляется `SUPABASE_URL`.

Серверный код поддерживает явно заданный `SERVER_DB_KEY`, встроенные современные `SUPABASE_SECRET_KEYS` (JSON с `default` или первым непустым строковым значением), а также старый `SUPABASE_SERVICE_ROLE_KEY`. Значения `sb_secret_...` отправляются только в заголовке `apikey`, legacy-ключ — также в `Authorization: Bearer`. Ключ базы никогда не нужен браузеру.

## Команды и работа бота

**Заявитель:** `/my` — только свои обращения, карточка, история, статус и «Написать уточнение». `/id` — только свой Telegram ID. Текст без привязки предлагает выбрать обращение.

**Владелец:** `/requests` — фильтры «Новые», «В работе», «Все», страницы по 8. Карточка: «Ответить», «История», «В работу», «Завершить». `/retry` — до 8 последних ошибок доставки с кнопками безопасного повтора. Проверка числового владельца повторяется при каждом callback.

Отвечать нужно через Reply на конкретную ForceReply-подсказку. База хранит связь `(chat_id, message_id подсказки)` с обращением. Поэтому ответы в обратном порядке по двум обращениям одного человека не смешиваются. История пагинируется по 5 сообщений, не удаляется при завершении.

Поддерживается только текст до 2000 символов. Вложения, голосовые, оплата и ИИ-ответы не реализуются.

## Путь обращения и защита

- На сайте только три поля: имя 1–80, тема 1–120, описание 5–2000 символов, счётчики, серверная проверка и поле-ловушка.
- POST создаёт **draft**, а не новую заявку. UUID — ключ идемпотентности. То же содержимое возвращает ту же действующую ссылку; другое содержимое с тем же UUID отклоняется.
- Непрозрачный код = HMAC-SHA256(UUID, FORM_SECRET), 43 URL-safe символа. В базе только SHA256 кода. Ссылка действует 30 минут.
- Только успешный Start в личном чате связывает запись с Telegram-аккаунтом и переводит её в `new`. Повторный Start не перепривязывает запись другому человеку.
- Статусы: `draft`, `new`, `in_progress`, `done`. Черновики скрыты из списков. Неподтверждённые черновики старше суток могут удаляться при новых формах. Подтверждённые записи и сообщения автоматически не удаляются.
- RLS включён на всех пяти таблицах. Прямой доступ `anon`, `authenticated` и PUBLIC к схеме, таблицам, последовательностям и RPC запрещён. Шесть публичных RPC доступны только `service_role`, с фиксированным безопасным `search_path`.
- CORS — точный origin сайта (без пути репозитория). Это ограничение браузера, а не авторизация. Проверка webhook — собственный секретный заголовок.
- Серверные лимиты: 10 форм с одного хешированного IP за 10 минут и 500 суммарно за UTC-сутки. Эти лимиты не отменяют квоты Supabase и не являются полной защитой от распределённой атаки. Платформенный reverse proxy должен предоставлять достоверный IP-заголовок; при его отсутствии приём отклоняется.
- В webhook проверяются private chat, совпадение `from.id` и `chat.id`, отсутствие bot-отправителя, принадлежность callback нашему боту, размеры и частота. Пользовательский текст отправляется без parse_mode.
- Логи приложения не содержат токенов и переписки. Платформа может вести собственные технические логи.

## Доставка и восстановление

Сообщение сначала фиксируется в базе вместе с outbox, затем отправляется. Отправителю отдельно сообщается сохранение, отдельно — подтверждённая Telegram доставка. Ошибка Telegram не отмечается успехом. «Доставлено Telegram» не означает «прочитано человеком».

Outbox постоянно хранит pending / processing / sent / failed, уникальный ключ эффекта, попытки и код ошибки. Захват использует `FOR UPDATE SKIP LOCKED`, случайный lease_token и аренду 90 секунд. Просроченная аренда восстанавливается следующей событийной обработкой webhook; если после аварии событий нет, владелец может отправить боту команду, чтобы запустить обработку. Никакого cron или таймера на минуту нет.

При слишком быстром ответе на ForceReply SQL откатывает обработку update_id с повторяемой ошибкой. Telegram повторно доставляет событие после записи привязки. При незавершённой очереди webhook отвечает 503, чтобы Telegram повторил доставку; уже сохранённый update_id не создаёт дубль.

После блокировки бота получателем ошибка остаётся в outbox. Получателю нужно разблокировать бота; владелец открывает `/retry` и повторяет выбранную ошибку. Постоянные ошибки не повторяются бесконечно без решения владельца. Если ошибка возникла после успешного sendMessage, но до записи результата в базу, теоретически возможна повторная доставка. **Exactly-once не обещается.**

При сбое Supabase: проверить состояние проекта и квоты, восстановить приостановленный проект в Dashboard, проверить webhook через getWebhookInfo. Не сбрасывать updates и не выполнять миграции повторно поверх существующих таблиц. Секрет FORM_SECRET не менять без необходимости: это влияет на ссылки неподтверждённых черновиков.

## Локальные команды

Нужен Node.js 22+ с npm. Зависимость PGlite нужна только для тестов; сайт и Edge Functions от npm не зависят.

```text
npm ci
npm test
npm run check
npm run preview
npm run bundle
```

Preview: `http://127.0.0.1:4173/university-future-requests/` — проверяет работу под путём репозитория. Это временный просмотр для разработки, **не сервер рабочего бота**.

Bundle создаёт три автономных файла `.local/dashboard/*.ts` без локальных импортов для Supabase Dashboard Editor. SQL-миграции и секреты размещаются отдельно. Обновление GitHub само по себе не обновляет Edge Functions и базу.

Дополнительно: `node scripts/owner.mjs` для ручного подтверждения своего ID из `/id`; `node scripts/telegram-setup.mjs register|status|test` вызывает только облачную setup-функцию. Токены не передаются в аргументах команд и не печатаются.

## Проверка и приёмка

21 локальная автоматическая проверка: настоящие SQL и PL/pgSQL в PGlite, два клиента и владелец через тестовый транспорт, повтор формы/Start/update_id, истечение ссылки, две заявки одного человека, чужой доступ, статусы, ошибки и retry, lease, быстрый ForceReply, секреты заголовков, CORS, типы/размеры/частота, современные ключи и URL Telegram.

На собственных опубликованных сервисах ещё нужна **явно обозначенная контрольная заявка** с владельцем: форма → Start → номер → /requests → ForceReply → фактический ответ → история → уточнение → статус. Проверить строки базы и outbox. Только после этого можно заявлять о живом запуске. Если доступен один Telegram-аккаунт, тест двух реальных заявителей не считается пройденным. Отдельно проверяется телефон при выключенном компьютере владельца.
